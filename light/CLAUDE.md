# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> **This is the active production implementation.** Maude Light is the only fully-shipped target. The parent repo (`../`) contains the long-term roadmap: macOS support, Linux VM-hosted sandboxes, Proxmox appliances, and a full multi-user appliance — but those targets are not yet production.

## Development Workflow: Agent Delegation (HIGH PRIORITY — standing instruction)

Same policy as the root `CLAUDE.md`, restated here since this file is meant to be self-contained: **all code and docs in `light/` must be written by background Sonnet agents, and all code changes must be reviewed by a separate background Fable agent** before being presented as complete or committed — every session, even when the orchestrating session is itself already Sonnet. ## What Maude Light is

A one-command Windows sandbox for agentic coding. A single PowerShell command installs an isolated Ubuntu WSL2 distro (`Maude`), mounts a shared folder on the Windows host (`%LOCALAPPDATA%\Maude\Data\Maude`), symlinks Claude Code config into that folder so settings survive reinstalls, and drops the user into a Textual TUI where they can create projects and open them in Claude Code.

**Goal**: a non-technical Windows user pastes one line into PowerShell and has a working AI coding environment in under 3 minutes.

## Architecture

```
Windows host
    |
    +-- %LOCALAPPDATA%\Maude\Data\Maude\          <- shared folder (default)
    |       +-- Projects/     <- coding projects (directly used by WSL)
    |       +-- .claude/      <- Claude Code config (symlinked from WSL home)
    |       +-- .kanna/       <- kanna web UI data (symlinked from WSL home)
    |
    +-- WSL2 distro: "Maude" (Ubuntu 26.04 default, 24.04 with -Noble flag)
          +-- ~/Maude/        <- drvfs mount of shared folder
          +-- ~/.claude       -> symlink to ~/Maude/.claude
          +-- ~/.kanna        -> symlink to ~/Maude/.kanna
          +-- ~/bin/          <- user scripts (front of PATH)
          +-- ~/.local/bin/   <- tool binaries (end of PATH)

Automount: disabled (no /mnt/c, /mnt/d — intentional security boundary)
Only mount: ~/Maude via /etc/fstab drvfs entry
```

`setup-wsl-maude.ps1` bakes packages into a reusable `Ubuntu-${ubuntuVersion}-Template` WSL distro first (`Ubuntu-26.04-Template` by default; `Ubuntu-24.04-Template` with `-Noble`), then imports it as `Maude`. Teardown + reinstall takes under a minute because the template is preserved.

**Two-path template build**: the template is created via either (a) the Microsoft Store path `wsl --install -d <distro> --name $TemplateName --no-launch` (used when `wsl --help` advertises `--name`), or (b) a fallback that `curl.exe`-downloads the Canonical rootfs and `wsl --import`s it into `$env:LOCALAPPDATA\Maude\Template` — WSL2 first, then WSL1 if WSL2 import fails. Rootfs URLs are hardcoded in `setup-wsl-maude.ps1`: `https://releases.ubuntu.com/noble/ubuntu-24.04.4-wsl-amd64.wsl` (`-Noble`) and `https://releases.ubuntu.com/resolute/ubuntu-26.04-wsl-amd64.wsl` (default). If a release URL changes upstream, update both paths.

**Release pinning & checksums**: `-Release main` (default) downloads scripts from `raw.githubusercontent.com/dirkpetersen/maude/main` with no verification. Any other `-Release <tag>` first fetches `light/checksums.txt` from that tag and SHA-256-verifies every downloaded file; a missing entry, empty file, or hash mismatch deletes the file and aborts with `exit 1`. `light/checksums.txt` is **not** auto-generated by CI (`release.yml` only hashes the WSL tarball) and is absent from the working tree — it must be regenerated and committed before pushing any `v*.*.*` tag, or pinned installs will fail with "Could not download checksums.txt".

**Security model**: automount disabled + no generic sudo = the AI agent can only reach the shared `Maude` folder and installed tools. Claude Code runs in `bypassPermissions` mode, which is safe inside the sandbox. A `~/.claude/yolo-mode` marker file enables this; delete it to restore normal permission prompts.

**Upstream repos** (checked out at `~/gh/` on the dev machine):
- `~/gh/web-term` — Node.js browser terminal via SSH+tmux (xterm.js frontend)
- `~/gh/appmotel` — Bash-based PaaS: deploys Python/Node/Go apps as systemd services behind Traefik
- `~/gh/mom` — Rust setuid tool allowing non-root users to install packages via apt/dnf

## Testing & linting

Tests live in `../tests/test-*.sh` (run from repo root). There is no test runner specific to `light/`; use the parent Makefile:

```bash
make test           # Run full test suite
make test-fast      # Stop on first failure
make lint           # Bash -n syntax check all scripts
bash tests/test-path-setup.sh   # Run one test file directly
```

Test helper API (source `tests/lib.sh`):

```bash
source "$(dirname "${BASH_SOURCE[0]}")/lib.sh"
suite_header "My feature"
assert_eq          "description" "expected" "$actual"
assert_contains    "description" "needle" "$haystack"
assert_file_exists "description" "/path/to/file"
assert_executable  "description" "/path/to/bin"
assert_exit_zero    "description" some_command --args
assert_exit_nonzero "description" some_command --args
skip "reason"
suite_summary   # prints results; exits non-zero if any FAIL
```

**Gotcha**: use `PASS=$((PASS+1))` not `((PASS++))` — the latter exits non-zero when the value is 0 under `set -e`.

**Coverage caveat**: most existing `tests/test-*.sh` files target the full-appliance code under `scripts/` and `packages/` only. The one exception is `tests/test-reviewer-libs.sh`, which covers the reviewer libs (`lib/llm-mode.sh`, `lib/codex.sh`, `lib/opencode.sh`, `lib/grok.sh`) — mode detection, skill fetch via `file://`, config-generator marker guards, and pipeline wiring. Everything else in `light/` remains untested — `setup-wsl-maude.ps1`, `teardown-wsl-maude.ps1`, `root-bootstrap.sh`, `maude-bootstrap.sh`, `maude`, `maude.py`, `MAUDE.md`, `statusline.sh` — and there are no PowerShell/Pester tests. When changing those files, smoke-test via the hot-patch workflow below, not the unit-test suite.

## Hot-patching during development

`setup-wsl-maude.ps1` downloads scripts from GitHub at install time, so testing local changes without a full reinstall requires one of:

- **Full reinstall** (~3 min): push to GitHub, then run `setup-wsl-maude.ps1`
- **Hot-patch bootstrap scripts**: pipe the changed file into the running distro, then re-run it manually:
  ```powershell
  Get-Content -Raw ".\root-bootstrap.sh" | wsl -d Maude -u root bash -c "cat > /tmp/root-bootstrap.sh && bash /tmp/root-bootstrap.sh"
  ```
- **Hot-patch `maude` CLI**:
  ```powershell
  Get-Content -Raw ".\maude" | wsl -d Maude -u maude bash -c "cat > ~/bin/maude && chmod +x ~/bin/maude"
  ```
- **Hot-patch `maude.py`**: copy to `~/.local/bin/maude.py` inside WSL, then delete the daily-update stamp to prevent auto-overwrite:
  ```bash
  date +%Y-%m-%d > ~/.maude-tui-last-update
  ```

## Key implementation patterns

### Piping files into WSL (no automount)
Automount is disabled, so `wslpath`/`cp` from Windows don't work. All file transfers use piped stdin:
```powershell
Get-Content -Raw ".\script.sh" | wsl -d Maude -u root bash -c "cat > /tmp/script.sh"
```
Package-install scripts use base64 to survive PowerShell's CRLF insertion:
```powershell
$encoded = [Convert]::ToBase64String([IO.File]::ReadAllBytes("script.sh"))
wsl -d Maude -- bash -c "echo '$encoded' | base64 -d | bash"
```

### Files downloaded at each lifecycle stage

Three separate download paths fetch files from `https://raw.githubusercontent.com/dirkpetersen/maude/$Release` — know which one to extend when adding a new file:

1. **Installer (`setup-wsl-maude.ps1`)** downloads exactly 7 files into `$env:TEMP\maude-setup` with a unix-timestamp cache-bust: `light/root-bootstrap.sh`, `light/maude-bootstrap.sh`, `light/maude`, `light/maude-shell.sh`, `light/welcome.sh`, `maude.png`, `packages/ubuntu-packages.yaml`. Checksums verified for pinned releases.
2. **Bootstrap (`maude-bootstrap.sh`)** re-fetches the eight `lib/*.sh` helpers (`ensure-tools.sh`, `refresh-md.sh`, `update-skills.sh`, `gemini.sh`, `llm-mode.sh`, `codex.sh`, `opencode.sh`, `grok.sh`) into `~/.local/lib/maude/` on every bootstrap run, then sources them (`llm-mode.sh` before the per-tool reviewer libs). Bootstrap also calls `refresh_claude_md` (downloads `MAUDE.md` + the one-time `CLAUDE.template.md`), `update_gemini` (downloads the repo-root `.claude/skills/gemini/SKILL.md` into `~/.claude/skills/gemini`), and then `update_codex`/`update_opencode`/`update_grok` right below it (warn-and-continue).
3. **CLI runtime (`maude` via `lib/refresh-md.sh`)** refreshes `MAUDE.md` at most once per day (stamp: `~/.local/share/maude/.last-md-refresh`), validates the download (≥200 bytes, starts with `# Maude Sandbox`), caches to `~/.local/share/maude/MAUDE.md`, falls through to the cache on failure.

When adding a new file under `light/`, decide which stage owns it: a new top-level script goes in the installer's `$filesToDownload`; a new `lib/*.sh` helper goes in the `for _lib in` loop in `maude-bootstrap.sh`; user-facing markdown that should refresh daily belongs alongside `MAUDE.md` in `refresh-md.sh`.

**Skill-loading gotcha**: Claude Code scans `~/.claude/skills/` only when it starts a *new* session. Both the `maude` CLI and the TUI's Open Project launch `claude <model> --continue`, which resumes the prior session and does NOT pick up skills installed/updated since that session began. So a `maude update` that refreshes the gemini or Anthropic skills won't surface them until the user starts fresh — via the TUI's **Clear context (no history)** checkbox (`fresh=True`, no `--continue`) or `claude opus` from a shell. `maude update` prints a note to this effect.

### `maude update` self-replace

`maude update` (`update_all()` in `light/maude`) downloads a fresh `maude` script to a sibling `${self_path}.new.$$` tmp file, sanity-checks it (shebang `#!/bin/bash`, size > 1024 bytes), diffs it against the running script, and `mv`s it over the running script only if different. This relies on Linux keeping the running script's open inode valid across `rename(2)` — the `mv` is safe to do mid-run. **Never replace this with `cat > "$self_path"`** — that would truncate the file the running shell is reading from and corrupt mid-execution. Rather than stopping there (which used to require a second `maude update` to actually run the new code), it immediately does `_MAUDE_UPDATE_STAGE2=1 exec "$self_path" update` — same PID, same terminal, replaces the process image with the freshly written script, which re-enters `update_all()` and (guarded by the `_MAUDE_UPDATE_STAGE2` env var, so it can't loop) skips straight past the self-update step into everything below. One `maude update` invocation now fully converges; the `exec` failing (essentially only a permissions edge case) is the sole fallback path that still needs a second run, and it says so explicitly.

### `maude update` parallel job batch

After the self-replace step, the network-bound updates run concurrently instead of one after another. `update_all()` backgrounds each step and tracks it via a per-job temp file pair allocated by `_alloc_job <name>`, which populates the associative arrays `JOUT[<name>]`/`JERR[<name>]` (stdout/stderr capture files, via `mktemp` with a deterministic fallback if `mktemp` fails) alongside `JPID`/`JRC` for PIDs and exit codes — there is no `job_tmp` directory and no `RETURN` trap (an earlier version used `trap 'rm -rf' RETURN`, which is buggy because bash fires RETURN traps on every `.`/source too, not just function return); the files are removed with a plain `rm -f "${JOUT[@]}"` / `rm -f "${JERR[@]}"` right before `update_all()`'s single `return`. Most batch-1 jobs (`claude update`, `~/.claude/statusline.sh`, `maude.py`, `bun install -g kanna-code`, the eight `lib/*.sh` downloads) redirect merged output with `> "${JOUT[name]}" 2>&1`, since they only ever print human status text. The batch-2 reviewer-CLI jobs (`update_skills`, `update_gemini`, `update_codex`, `update_opencode`, `update_grok`) instead split streams — `> "${JOUT[name]}" 2> "${JERR[name]}"` — because their stdout carries the parsed `cli:`/`skill:`/`config:` status lines (or a bare count, for skills) that the print phase formats into green/yellow result lines, while stderr carries incidental human warnings from the underlying installers; the print phase surfaces any non-empty `${JERR[name]}` content as its own yellow `!` line so a real installer warning can never get mistaken for, or swallowed into, a green success line. Two batches, gated by one dependency: **batch 1** — the jobs above — starts immediately; `update_all()` waits for **only** the libs job (the reviewer-CLI functions live in those libs), re-sources the fresh copies, then fires **batch 2**, which runs alongside anything still finishing from batch 1. Everything else waits on the full batch (`for jname in "${!JPID[@]}"; do wait ...; done`, skipping the libs job already waited on) before continuing.

**Deliberately excluded from the parallel batch**: `mom upgrade -y` (and the `dbus-user-session` install ahead of it) — apt/dpkg operations don't compose safely with concurrent runs, so they stay solo and run after the parallel batch's `wait`, exactly where they always did.

**Two shared-file hazards, two locks**: (1) **`~/.bashrc`** — `update_codex` and `update_grok` each run a vendor installer that *appends* a PATH block to `~/.bashrc`, then strip that block back out with `sed -i` (whole-file read → temp write → rename), because the block would land after `maude-path.sh` and put `~/.local/bin` ahead of `~/bin` on PATH. Run concurrently, either half of that sequence can interleave with the other tool's — an append landing mid-strip, or two `sed -i` renames racing — so each function acquires the shared advisory lock `$HOME/.bashrc.lock` (fd 200, `flock -w 600 200`) *before* invoking its installer and holds it through the strip and the `.bashrc.bak.*` sweep, releasing only afterward (`flock -u 200`); codex and grok are the only two `~/.bashrc` writers in the parallel batch, so this fully serializes their install+strip against each other. `update_grok`'s installer leg is additionally wrapped in `timeout 300` (defense-in-depth beyond curl's own `--max-time`, since a hung `sh` after the pipe wouldn't otherwise be bounded) so a stuck install can't pin the lock indefinitely. (2) **the bun/npm global package store** — the inline `bun install -g kanna-code` batch-1 job, `update_gemini`'s and `update_opencode`'s `bun install -g` calls, and the `npm install -g` fallbacks in `update_codex`/`update_grok` all share one global store that doesn't tolerate concurrent writers, so each wraps its install in `flock -w 600 9 ... 9>"$HOME/.maude-pkg-install.lock"`. Lock ordering is deadlock-safe: fd 200 (`.bashrc.lock`) is always acquired before fd 9 (`.maude-pkg-install.lock`) inside codex/grok, and nothing that holds fd 9 ever reaches for fd 200, so there is no cycle. (Verified with a concurrent stress test exercising the lock against itself, which passed reliably with the lock held and failed without it.) No other job touches a file another job also touches — `update_skills` writes only its own `~/.claude/skills/{claude-api,doc-coauthoring,...}` subdirs, distinct from the per-tool skill/config paths.

The rest of the command runs sequentially, after the join, in this order: shell environment exports — idempotently appends `COLORTERM=truecolor`, `PYTHONDONTWRITEBYTECODE=1`, `GEMINI_CLI_TRUST_WORKSPACE=true` to `~/.bashrc` if missing; `python3 maude.py --fix-bashrc` — repairs orphan `fi` artefacts left by an older buggy keychain stripper (needs the freshly downloaded `maude.py`, and needs codex/grok's `~/.bashrc` edits finished — both guaranteed by the join); systemd user-session health check — unmasks `user@.service` if an old bootstrap masked it (prints `wsl -d Maude -u root` one-liner when root is required), installs `dbus-user-session` via mom if missing; `ensure_textual` — enforces the pin `textual>=8.2.4,<9`; prints the kanna/gemini/codex/opencode/grok results captured from the parallel batch above; `ensure_tool_symlinks`; `mom upgrade -y` — gated on `mom >= 0.2.20`, compares systemd version before/after and warns to run `wsl --shutdown` if it changed; prints the `update_skills` result captured from the parallel batch; writes the version stamp (`~/.local/share/maude/version`) from git or the GitHub API and prints it. When adding a new auto-updatable network-bound component, add it to the parallel batch (respecting the libs-first / no-bashrc-race constraints above); local/fast or package-manager steps stay sequential.

### `MAUDE_RAW` environment override

`maude-bootstrap.sh`, the `maude` CLI, and `lib/refresh-md.sh` all honor `MAUDE_RAW` to override the GitHub raw base URL (default `https://raw.githubusercontent.com/dirkpetersen/maude/main/light`). Setting it lets contributors test fork/branch changes without merging to `main` — e.g. `MAUDE_RAW=https://raw.githubusercontent.com/me/maude/feature/light maude tui`. `root-bootstrap.sh` hardcodes the URL and does NOT honor the override (it runs once at install time from `setup-wsl-maude.ps1`, which uses its own `-Release <tag>` flag with checksum verification for the same purpose).

### Two-phase bootstrap
`root-bootstrap.sh` writes `/etc/wsl.conf` (`automount=false`, default user, `interop=false`) and `/etc/fstab`. These only take effect after `wsl --terminate`. The setup script terminates WSL after root-bootstrap, then runs `maude-bootstrap.sh` as the maude user in the restarted distro.

### Host-persistent paths
`~/.claude` and `~/.kanna` are symlinks to `~/Maude/.claude` and `~/Maude/.kanna`. These survive WSL distro teardown/reinstall because they live on the Windows drvfs mount. Any file that must survive reinstall must live there.

### Sandbox docs lifecycle

Three sandbox-facing docs live in `light/` with distinct lifecycles — easy to confuse:

- `light/MAUDE.md` — sandbox rules for the AI agent. Refreshed daily by `refresh_claude_md()` in `lib/refresh-md.sh`: downloaded to a tempfile, validated (non-empty, ≥200 bytes, first line matches `^# Maude Sandbox` — defends against corporate-proxy HTML interception), then moved to the cache at `~/.local/share/maude/MAUDE.md` and always `cp -f`'d over `~/.claude/MAUDE.md`. The `maude` CLI also re-runs this refresh on each project open, so edits to `~/.claude/MAUDE.md` are silently overwritten — change `light/MAUDE.md` instead.
- `light/CLAUDE.template.md` — 7-line user-instructions template. Copied to `~/.claude/CLAUDE.md` **only if that file does not already exist**. The template loads MAUDE.md via `@MAUDE.md` on line 2 — do not remove that line.
- `light/DANGER-ZONE.txt` — plain-English safety warning for the shared host folder. Auto-restored on each login by `welcome.sh` if missing from `~/Maude/DANGER-ZONE.txt`. References Microsoft Azure and Amazon Web Services as cloud AI providers and the SLAs/DPAs governing data handling.

### Login-time shell wiring (`welcome.sh` + `maude-shell.sh`)

Both files are installed as `/etc/profile.d/maude-welcome.sh` and `/etc/profile.d/maude-shell.sh` by `root-bootstrap.sh`, which also appends explicit `. /etc/profile.d/maude-*.sh` lines to `/etc/skel/.bashrc` and the active user's `~/.bashrc` (profile.d only auto-runs for login shells, so the `.bashrc` hook is required for non-login interactive shells).

- `welcome.sh`: auto-restores `~/Maude/DANGER-ZONE.txt` if missing (`curl --max-time 10`). Then bootstraps keychain via `eval "$(keychain --quiet --noask --eval --agents ssh)"`; if `~/.ssh/id_ed25519` or `~/.ssh/id_rsa` exists and its fingerprint is not already loaded, prints a colored "Unlock your GitHub SSH key" prompt and runs `keychain --quiet --eval --agents ssh <key>`. After keychain, if the TUI is enabled it runs `maude tui` and returns; the static ASCII welcome banner is the fallback for opt-out users (appends a yellow "Set Creds" nudge when neither `~/.aws/credentials` nor `~/.azure/clauderc` exists). All branches gate on `MAUDE_WELCOMED` so re-sourcing from `.bashrc` doesn't re-trigger.
- `maude-shell.sh`: exports `PIP_BREAK_SYSTEM_PACKAGES=1` (safe inside the sandbox — pip without a venv is intentional) and `COLORTERM=truecolor` (Windows Terminal renders 24-bit natively; this hint makes vim/tmux/fzf emit true-color escapes — `TERM` stays `xterm-256color`); sets `PS1` to `user@_:cwd$` (literal underscore in place of the hostname so the WSL distro name doesn't leak into the prompt); defines `menu()` as a shortcut for `maude tui`; overrides bare `help` to print "Please type 'maude help <ENTER>' for help" (delegates to `builtin help` when given args); and registers `complete -F _maude_complete maude` for tab completion of subcommands plus project names from `~/Maude/Projects/`.

### Double brackets in bash
Always use `[[ ]]` not `[ ]` in bash conditionals.

### `curl.exe` not `curl` in PowerShell
`curl` in PowerShell aliases to `Invoke-WebRequest`. Always use `curl.exe` explicitly. Also note `iex` may be blocked by antivirus on corporate machines.

### WSL encoding gotcha
`wsl.exe --list --verbose` outputs UTF-16LE with BOM. Strip null bytes before parsing:
```powershell
$raw   = wsl.exe --list --verbose | Out-String
$clean = $raw -replace "`0", ""
```

### Windows Terminal profiles
WT auto-generates profiles with `source=Microsoft.WSL` — they cannot be deleted, only hidden with pre-hidden stubs. WT profile cleanup must run **before** self-elevation (elevated process has a different `$env:LOCALAPPDATA`).

## Maude TUI (`maude tui` / `maude.py`)

Full-screen Textual TUI — default welcome experience for every new terminal session.

```
┌─ Maude ──────────────────────────────────────────────────────────────┐
│  ASCII logo (green)         │  Projects                              │
│  ──────────────             │ ┌────────────────────────────────────┐ │
│  Start TUI with Maude  [x]  │ │ banana    Modified: Apr 10, 2026   │ │
│  ──────────────             │ │ my-app    Modified: Apr 9, 2026    │ │
│  Tips:                      │ │ ...                                │ │
│   Screen split  Alt+Sh+±    │ └────────────────────────────────────┘ │
│   Share image  drop file    │                                        │
│   Voice  Win+H              │                                        │
│  ──────────────             │                                        │
│  Claude model               │                                        │
│   ( ) opus  ( ) fable       │                                        │
│   ( ) sonnet  ( ) haiku     │                                        │
├─────────────────────────────┴──────────────────────────────────────────────────────────────┤
│ [Open Project] [+ New] [Web UI] [To Github] [Setup Git(hub)] [Set Creds] [Command Line]    │
└────────────────────────────────────────────────────────────────────────────────────────────┘
```

**Key behaviors:**
- **Open project**: `app.suspend()` → `claude <model> --continue` (fallback: `claude <model>` if `--continue` exits non-zero) → resume TUI; cursor restored to the project just opened. The sidebar **Clear context (no history)** checkbox (`#fresh-context`, below the model picker) sets `fresh=True`, which makes `open_project()` skip `--continue` and start Claude with no prior history
- **Delete**: confirm modal → soft-delete to `Projects/.deleted/` (not permanent)
- **New project**: modal, spaces auto-replaced with hyphens, git init
- **Web UI**: launches kanna with `CLAUDE_EXECUTABLE=$HOME/bin/claude` so the wrapper sets auth env vars (Foundry/Azure/Bedrock/direct). Click again to stop — `SIGTERM` → `SIGKILL` + `fuser -k 3210/tcp`. Refuses to launch without credentials; pops `CredsEntryScreen` as recovery
- **To Github**: dual-mode push/detach for the selected project. If `origin` already points to GitHub, opens `DetachFromGithubScreen` which removes the local `origin` remote only — it explicitly does NOT delete the GitHub-side repo (leaves it orphaned; must be deleted manually on github.com). Otherwise opens `PushToGithubScreen`, which: (1) auto-seeds a minimal `README.md` (`# {repo}\n`) if none exists in any case variant, (2) forces `GIT_SSH_COMMAND='ssh -o BatchMode=yes -o StrictHostKeyChecking=accept-new'` so a misconfigured SSH state errors in 5-10s instead of blocking on a passphrase prompt, (3) short-circuits with a clear error and auto-pops `SSHKeyUnlockScreen` if the SSH key has a passphrase but no agent has it loaded, (4) runs `gh repo create --push` for new repos or `git push -u origin HEAD` for existing ones, creating an initial commit first if the project has no HEAD
- **SSH key unlock at TUI mount**: on mount (and again after `CredsEntryScreen` closes), if `~/.ssh/id_ed25519` exists, an ssh-agent is reachable (`ensure_ssh_agent()` will spin one up), and the key isn't already loaded, the TUI auto-pops `SSHKeyUnlockScreen` for the passphrase — or silently runs `ssh-add` with an empty passphrase if the key is unencrypted. This is the deliberate counterpart to the Setup Git wizard's keychain block (which omits a key file on purpose). If you ever "fix" the wizard by passing the key to `keychain`, you'll re-introduce an early `.bashrc` prompt before the TUI is visible — leave the unlock to the TUI
- **Setup Git(hub)**: `GitSetupWizard` 4-step modal — (1) GitHub username → `api.github.com/users/<name>` lookup pre-fills name/email (email falls back to `<id>+<login>@users.noreply.github.com` when hidden); (2) ed25519 SSH key detect/generate + verify via `ssh -T git@github.com` (manual paste of the pubkey to github.com); (3) `gh auth login --hostname github.com --git-protocol ssh --web --scopes write:gpg_key`, then silently generates an ed25519+cv25519 GPG signing key (no passphrase) and uploads it via `gh gpg-key add` — no separate GPG step is shown to the user; (4) `git config user.name`/`user.email`/`init.defaultBranch=main` (plus `user.signingkey` + `commit.gpgsign=true` when GPG was provisioned), `mom install -y keychain`, and a sentinel-bracketed (`# >>> Maude keychain BEGIN`/`END`) keychain block appended to `~/.bashrc`. The keychain block intentionally does NOT pass a key file — `SSHKeyUnlockScreen` handles the passphrase prompt at TUI startup instead, so `.bashrc` doesn't block on a prompt before the TUI appears
- **Claude model picker**: 4-button radio (`opus` default, `fable`, `sonnet`, `haiku`). Persists to `~/.maude-model`
- **Credential gate**: `CredsEntryScreen` blocks startup when no LLM credentials are found — checks a native claude.ai login (`have_claude_login()`: non-empty `claudeAiOauth.accessToken` in `~/.claude/.credentials.json` with `expiresAt` in the future, mirroring `_is_claude_logged_in()` in the dok claude-wrapper), `ANTHROPIC_API_KEY`, `ANTHROPIC_FOUNDRY_API_KEY`, non-empty `~/.aws/credentials`, or non-empty `~/.azure/clauderc`. Three mode tabs plus one action button. **Claude Login** (next to Azure Foundry) suspends the TUI and runs the **unwrapped** `~/.local/bin/claude /login` — unwrapped because with zero cloud creds the `~/bin/claude` wrapper exits "No valid configuration found" before Claude Code starts, so `/login` could never complete through it; interop is off, so the user copy/pastes the OAuth URL into a Windows browser manually. On return, a valid token dismisses the modal as saved (pending action proceeds); otherwise a status hint shows. The wrapper prefers a native login over Foundry/Bedrock, and `--az`/`--aws` force a specific cloud per-run. The three mode tabs: **Paste exports** (parses `export KEY=VAL` / `KEY=VAL` lines whose key starts with `ANTHROPIC_*/CLAUDE_*/AWS_*/AZURE_*/OPENAI_*/GEMINI_*/GOOGLE_*`, merges into `~/.azure/clauderc` mode 0600 — **except** `GEMINI_*`/`GOOGLE_*`, which are split out to `~/.gemini/.env` (dotenv format, mode 0600) where the Gemini CLI auto-loads them; those exist solely to feed the gemini-cli skill, do NOT touch clauderc, and do NOT satisfy the Claude-credential startup gate; there is intentionally no Gemini tab/button. Empty-valued lines (`FOO=`) are dropped. `finalize_gemini_vals()` then picks a Gemini-CLI auth mode that actually authenticates: a bare API key (`GEMINI_API_KEY`, or `GOOGLE_API_KEY` mapped onto it) is routed to **AI Studio**, which accepts API keys with no OAuth; **Vertex** (`GOOGLE_GENAI_USE_VERTEXAI=true`) is enabled only on real intent — the flag is in *that* paste, or a service account / ADC (`GOOGLE_APPLICATION_CREDENTIALS`) is configured — because Vertex *rejects* plain API keys for `generateContent`. When an API key is used, any stale `GOOGLE_GENAI_USE_VERTEXAI=true` is flipped back to `false` so the user isn't trapped on the Vertex path; Vertex-with-no-region defaults to `us-west1`/Oregon (`DEFAULT_VERTEX_LOCATION`). The gemini CLI's untrusted-directory gate is bypassed via `GEMINI_CLI_TRUST_WORKSPACE=true` (set in `maude-shell.sh`) plus `--skip-trust` in the skill); **AWS Bedrock** (writes `~/.aws/credentials` + `~/.aws/config` under a `[bedrock]` named profile, also stashes `AWS_*` + `CLAUDE_CODE_USE_BEDROCK=1` in clauderc); **Azure Foundry** (URL + API key → clauderc with `CLAUDE_CODE_USE_FOUNDRY=1`). When *both* Bedrock and Foundry creds exist, a "Default to AWS Bedrock" checkbox appears that physically renames `~/.azure/clauderc` ↔ `~/.azure/clauderc.inactive` so the claude wrapper doesn't re-source Foundry creds when Bedrock should win
- **Auto-launch**: `welcome.sh` (installed by `root-bootstrap.sh` to `/etc/profile.d/maude-welcome.sh` and *also* explicitly sourced from `~/.bashrc` to cover non-login interactive shells) runs `maude tui` when all four guards hold: `[[ -t 1 ]]` (stdout is a TTY), `MAUDE_WELCOMED` is unset (set on first run to prevent re-launch when `.bashrc` re-sources the script), `~/.maude-tui-disabled` does NOT exist, and `maude` is on PATH. The sidebar checkbox is an OPT-OUT bound to `not DISABLE_FLAG.exists()`: unchecking touches `~/.maude-tui-disabled`, rechecking unlinks it. The legacy `~/.maude-tui-autostart` flag is no longer consulted — remove references when seen
- **Daily self-update**: `maybe_self_update()` runs at module entry, before `app.run()`. Compares `~/.maude-tui-last-update` (format: `YYYY-MM-DD`) against today; if stale and time ≥ noon local, downloads fresh copy from GitHub and atomically replaces itself. New code takes effect on next launch
- **Status line**: `~/.claude/statusline.sh` renders cwd + remaining context-window %. Bootstrap merges this into `~/.claude/settings.json` `statusLine.command` without overwriting existing user customisations
- **Exit hint**: after quitting TUI prints "Please type menu \<Enter\> to get back to the TUI or type maude help \<Enter\>"
- **Colors**: green logo, dusty-rose accents, warm-grey toggles (overrides Textual default blue on `Checkbox`/`RadioButton`)
- **Dependency**: `textual` — installed via `pip install textual` in `maude-bootstrap.sh`; pin `textual>=8.2.4,<9` — 8.2.3 (and only 8.2.3) crashes `CredsEntryScreen` with `KeyError: text-area--gutter` (textual#6528, verified empirically against every 8.x release); `<9` shields auto-updating machines from an unknown future major break
- **`maude.py` CLI flags** (exit before `maybe_self_update()` and the TUI): `--github` runs `GitSetupWizard` standalone in a minimal `_WizardApp` (invoked by `maude github`); `--fix-bashrc` runs `fix_bashrc_orphan_fi()` to repair `~/.bashrc` damage left by an older buggy keychain stripper (invoked by `maude update`). The orphan-fi repair function looks unused but is load-bearing — do not remove during dead-code cleanups

## PATH convention

`~/bin` must be at the **front** of PATH; `~/.local/bin` must also be present. `maude-path.sh` (written to `/etc/profile.d/` by `root-bootstrap.sh`) runs at the **end** of `~/.bashrc` — after tool installers like Claude Code that prepend their own paths — then re-enforces `~/bin` first and deduplicates `~/.local/bin`.

## Credential forwarding (kanna web UI)

Kanna is launched with `CLAUDE_EXECUTABLE=$HOME/bin/claude` so it shells out to the Maude wrapper, which sets the appropriate auth env vars per invocation. If the wrapper is missing, the env var is unset and kanna falls back to plain `claude` on PATH.

|-------------------|---------|
