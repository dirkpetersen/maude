## What Maude Light is

A one-command Windows sandbox for agentic coding. A single PowerShell command installs an isolated Ubuntu WSL2 distro (`Maude`), mounts a shared folder on the Windows host (`%LOCALAPPDATA%\Maude\Data\Maude`), symlinks Claude Code config into that folder so settings survive reinstalls, and drops the user into a Textual TUI where they can create projects and open them in Claude Code.

**Goal**: a non-technical Windows user pastes one line into PowerShell and has a working AI coding environment in under 3 minutes.

## Architecture

```
Windows host
    |
    +-- %LOCALAPPDATA%\Maude\Data\Maude\          <- shared folder (default)
    |       +-- Projects/     <- coding projects (directly used by WSL)
    |       +-- .claude/      <- Claude Code config (symlinked from WSL home)
    |       +-- .kanna/       <- kanna web UI data (only .kanna/data is linked from WSL home)
    |
    +-- WSL2 distro: "Maude" (Ubuntu 26.04 default, 24.04 with -Noble flag)
          +-- ~/Maude/        <- drvfs mount of shared folder
          +-- ~/.claude       -> symlink to ~/Maude/.claude
          +-- ~/.kanna        local dir; ~/.kanna/data -> ~/Maude/.kanna/data
          +-- ~/bin/          <- user scripts (front of PATH)
          +-- ~/.local/bin/   <- tool binaries (end of PATH)

Automount: disabled (no /mnt/c, /mnt/d — intentional security boundary)
Only mount: ~/Maude via /etc/fstab drvfs entry
```

`setup-wsl-maude.ps1` bakes packages into a reusable `Ubuntu-${ubuntuVersion}-Template` WSL distro first (`Ubuntu-26.04-Template` by default; `Ubuntu-24.04-Template` with `-Noble`), then imports it as `Maude`. Teardown + reinstall takes under a minute because the template is preserved.

**Two-path template build**: the template is created via either (a) the Microsoft Store path `wsl --install -d <distro> --name $TemplateName --no-launch` (used when `wsl --help` advertises `--name`), or (b) a fallback that `curl.exe`-downloads the Canonical rootfs and `wsl --import`s it into `$env:LOCALAPPDATA\Maude\Template` — WSL2 first, then WSL1 if WSL2 import fails. Rootfs URLs are hardcoded in `setup-wsl-maude.ps1`: `https://releases.ubuntu.com/noble/ubuntu-24.04.4-wsl-amd64.wsl` (`-Noble`) and `https://releases.ubuntu.com/resolute/ubuntu-26.04-wsl-amd64.wsl` (default). If a release URL changes upstream, update both paths.

**Release pinning & checksums**: `-Release main` (default) downloads scripts from `raw.githubusercontent.com/dirkpetersen/maude/main` with no verification. Any other `-Release <tag>` first fetches `light/checksums.txt` from that tag and SHA-256-verifies every downloaded file; a missing entry, empty file, or hash mismatch deletes the file and aborts with `exit 1`. `light/checksums.txt` (lines `<sha256>  <path>`) is generated by `scripts/gen-checksums.sh`, which reads the `Key = "..."` entries of `$filesToDownload` in `setup-wsl-maude.ps1` and hashes the **git blob** bytes at HEAD (what raw.githubusercontent.com serves — not the CRLF working tree). `make tag VERSION=vX.Y.Z` regenerates it, commits it ("chore(release): checksums for vX.Y.Z") and pushes before creating the tag; the `verify-checksums` job in `release.yml` (`gen-checksums.sh --check`) fails the release early if the file is missing or stale at the tagged commit. After changing the installer's download list or any listed file, re-run the generator before tagging. Tested by `tests/test-checksums.sh`.

**Security model**: automount disabled + no generic sudo = the AI agent can only reach the shared `Maude` folder and installed tools. Claude Code runs in `bypassPermissions` mode, which is safe inside the sandbox. A `~/.claude/yolo-mode` marker file enables this; delete it to restore normal permission prompts.

**Upstream repos** (checked out at `~/gh/` on the dev machine):
- `~/gh/web-term` — Node.js browser terminal via SSH+tmux (xterm.js frontend)
- `~/gh/appmotel` — Bash-based PaaS: deploys Python/Node/Go apps as systemd services behind Traefik
- `~/gh/mom` — Rust setuid tool allowing non-root users to install packages via apt/dnf

## Testing & linting

Tests live in `../tests/test-*.sh` (run from repo root). There is no test runner specific to `light/`; use the parent Makefile:

```bash
make test           # Run full test suite
make test-fast      # Stop on first failure
make lint           # Bash -n syntax check all scripts
bash tests/test-path-setup.sh   # Run one test file directly
```

Test helper API (source `tests/lib.sh`):

```bash
source "$(dirname "${BASH_SOURCE[0]}")/lib.sh"
suite_header "My feature"
assert_eq          "description" "expected" "$actual"
assert_contains    "description" "needle" "$haystack"
assert_file_exists "description" "/path/to/file"
assert_executable  "description" "/path/to/bin"
assert_exit_zero    "description" some_command --args
assert_exit_nonzero "description" some_command --args
skip "reason"
suite_summary   # prints results; exits non-zero if any FAIL
```

**Gotcha**: use `PASS=$((PASS+1))` not `((PASS++))` — the latter exits non-zero when the value is 0 under `set -e`.

**Coverage caveat**: most existing `tests/test-*.sh` files target the full-appliance code under `scripts/` and `packages/` only. The one exception is `tests/test-reviewer-libs.sh`, which covers the reviewer libs (`lib/llm-mode.sh`, `lib/codex.sh`, `lib/opencode.sh`, `lib/grok.sh`) — mode detection, skill fetch via `file://`, config-generator marker guards, and pipeline wiring. Everything else in `light/` remains untested — `setup-wsl-maude.ps1`, `teardown-wsl-maude.ps1`, `root-bootstrap.sh`, `maude-bootstrap.sh`, `maude`, `maude.py`, `MAUDE.md`, `statusline.sh` — and there are no PowerShell/Pester tests. When changing those files, smoke-test via the hot-patch workflow below, not the unit-test suite.

## Hot-patching during development

`setup-wsl-maude.ps1` downloads scripts from GitHub at install time, so testing local changes without a full reinstall requires one of:

- **Full reinstall** (~3 min): push to GitHub, then run `setup-wsl-maude.ps1`
- **Hot-patch bootstrap scripts**: pipe the changed file into the running distro, then re-run it manually:
  ```powershell
  Get-Content -Raw ".\root-bootstrap.sh" | wsl -d Maude -u root bash -c "cat > /tmp/root-bootstrap.sh && bash /tmp/root-bootstrap.sh"
  ```
- **Hot-patch `maude` CLI**:
  ```powershell
  Get-Content -Raw ".\maude" | wsl -d Maude -u maude bash -c "cat > ~/bin/maude && chmod +x ~/bin/maude"
  ```
- **Hot-patch `maude.py`**: copy to `~/.local/bin/maude.py` inside WSL, then delete the daily-update stamp to prevent auto-overwrite:
  ```bash
  date +%Y-%m-%d > ~/.maude-tui-last-update
  ```

## Key implementation patterns

### Piping files into WSL (no automount)
Automount is disabled, so `wslpath`/`cp` from Windows don't work. All file transfers use piped stdin:
```powershell
Get-Content -Raw ".\script.sh" | wsl -d Maude -u root bash -c "cat > /tmp/script.sh"
```
Package-install scripts use base64 to survive PowerShell's CRLF insertion:
```powershell
$encoded = [Convert]::ToBase64String([IO.File]::ReadAllBytes("script.sh"))
wsl -d Maude -- bash -c "echo '$encoded' | base64 -d | bash"
```

### Files downloaded at each lifecycle stage

Three separate download paths fetch files from `https://raw.githubusercontent.com/dirkpetersen/maude/$Release` — know which one to extend when adding a new file:

1. **Installer (`setup-wsl-maude.ps1`)** downloads exactly 8 files into `$env:TEMP\maude-setup` with a unix-timestamp cache-bust: `light/root-bootstrap.sh`, `light/maude-bootstrap.sh`, `light/maude`, `light/maude-shell.sh`, `light/welcome.sh`, `light/welcome-stub.sh`, `maude.png`, `packages/ubuntu-packages.yaml`. Checksums verified for pinned releases. Both welcome files are piped in: `light/welcome.sh` as `/tmp/maude-welcome.sh` (used to seed the user-owned `~/.local/lib/maude/welcome.sh`) and `light/welcome-stub.sh` as `/tmp/maude-welcome-stub.sh` (installed to `/etc/profile.d/maude-welcome.sh`) — piping the stub keeps it offline-safe and SHA-verified for pinned releases (it's root-owned code sourced by every login shell), with `root-bootstrap.sh`'s direct `curl` of `$GH_RAW/welcome-stub.sh` as the fallback for the non-piped path.
2. **Bootstrap (`maude-bootstrap.sh`)** re-fetches the ten `lib/*.sh` helpers (`cli-tools.sh`, `ensure-tools.sh`, `refresh-md.sh`, `update-skills.sh`, `gemini.sh`, `llm-mode.sh`, `codex.sh`, `opencode.sh`, `grok.sh`, `kanna.sh`) into `~/.local/lib/maude/` on every bootstrap run, then sources them (`llm-mode.sh` before the per-tool reviewer libs). Bootstrap also calls `refresh_claude_md` (downloads `MAUDE.md` + the one-time `CLAUDE.template.md`), `update_gemini` (downloads the repo-root `.claude/skills/gemini/SKILL.md` into `~/.claude/skills/gemini`), and then `update_codex`/`update_opencode`/`update_grok` right below it, then `update_kiro`/`update_crush` (install-if-missing) and `link_kiro_skills` (all warn-and-continue).
3. **CLI runtime (`maude` via `lib/refresh-md.sh`)** refreshes `MAUDE.md` at most once per day (stamp: `~/.local/share/maude/.last-md-refresh`), validates the download (≥200 bytes, starts with `# Maude Sandbox`), caches to `~/.local/share/maude/MAUDE.md`, falls through to the cache on failure.

When adding a new file under `light/`, decide which stage owns it: a new top-level script goes in the installer's `$filesToDownload`; a new `lib/*.sh` helper goes in the `for _lib in` loop in `maude-bootstrap.sh`; user-facing markdown that should refresh daily belongs alongside `MAUDE.md` in `refresh-md.sh`.

**Skill-loading gotcha**: Claude Code scans `~/.claude/skills/` only when it starts a *new* session. Both the `maude` CLI and the TUI's Open Project launch `claude <model> --continue`, which resumes the prior session and does NOT pick up skills installed/updated since that session began. So a `maude update` that refreshes the gemini or Anthropic skills won't surface them until the user starts fresh — via the TUI's **Clear History** checkbox (`fresh=True`, no `--continue`) or `claude opus` from a shell. `maude update` prints a note to this effect.

### `maude update` self-replace

`maude update` (`update_all()` in `light/maude`) downloads a fresh `maude` script to a sibling `${self_path}.new.$$` tmp file, sanity-checks it (shebang `#!/bin/bash`, size > 1024 bytes), diffs it against the running script, and `mv`s it over the running script only if different. This relies on Linux keeping the running script's open inode valid across `rename(2)` — the `mv` is safe to do mid-run. **Never replace this with `cat > "$self_path"`** — that would truncate the file the running shell is reading from and corrupt mid-execution. Rather than stopping there (which used to require a second `maude update` to actually run the new code), it immediately does `_MAUDE_UPDATE_STAGE2=1 exec "$self_path" update` — same PID, same terminal, replaces the process image with the freshly written script, which re-enters `update_all()` and (guarded by the `_MAUDE_UPDATE_STAGE2` env var, so it can't loop) skips straight past the self-update step into everything below. One `maude update` invocation now fully converges; the `exec` failing (essentially only a permissions edge case) is the sole fallback path that still needs a second run, and it says so explicitly.

### `maude update` parallel job batch

After the self-replace step, the network-bound updates run concurrently instead of one after another. `update_all()` backgrounds each step and tracks it via a per-job temp file pair allocated by `_alloc_job <name>`, which populates the associative arrays `JOUT[<name>]`/`JERR[<name>]` (stdout/stderr capture files, via `mktemp` with a deterministic fallback if `mktemp` fails) alongside `JPID`/`JRC` for PIDs and exit codes — there is no `job_tmp` directory and no `RETURN` trap (an earlier version used `trap 'rm -rf' RETURN`, which is buggy because bash fires RETURN traps on every `.`/source too, not just function return); the files are removed with a plain `rm -f "${JOUT[@]}"` / `rm -f "${JERR[@]}"` right before `update_all()`'s single `return`. Most batch-1 jobs (`claude update`, `~/.claude/statusline.sh`, `maude.py`, `bun install -g kanna-code`, the ten `lib/*.sh` downloads) redirect merged output with `> "${JOUT[name]}" 2>&1`, since they only ever print human status text. The batch-2 reviewer-CLI jobs (`update_skills`, `update_gemini`, `update_codex`, `update_opencode`, `update_grok`, plus the install-if-missing `update_kiro` and `update_crush`) instead split streams — `> "${JOUT[name]}" 2> "${JERR[name]}"` — because their stdout carries the parsed `cli:`/`skill:`/`config:` status lines (or a bare count, for skills) that the print phase formats into green/yellow result lines, while stderr carries incidental human warnings from the underlying installers; the print phase surfaces any non-empty `${JERR[name]}` content as its own yellow `!` line so a real installer warning can never get mistaken for, or swallowed into, a green success line. Two batches, gated by one dependency: **batch 1** — the jobs above — starts immediately; `update_all()` waits for **only** the libs job (the reviewer-CLI functions live in those libs), re-sources the fresh copies, then fires **batch 2**, which runs alongside anything still finishing from batch 1. Everything else waits on the full batch (`for jname in "${!JPID[@]}"; do wait ...; done`, skipping the libs job already waited on) before continuing.

**Deliberately excluded from the parallel batch**: `mom upgrade -y` (and the `dbus-user-session` install ahead of it) — apt/dpkg operations don't compose safely with concurrent runs, so they stay solo and run after the parallel batch's `wait`, exactly where they always did.

**Two shared-file hazards, two locks**: (1) **`~/.bashrc`** — `update_codex` and `update_grok` each run a vendor installer that *appends* a PATH block to `~/.bashrc`, then strip that block back out with `sed -i` (whole-file read → temp write → rename), because the block would land after `maude-path.sh` and put `~/.local/bin` ahead of `~/bin` on PATH. Run concurrently, either half of that sequence can interleave with the other tool's — an append landing mid-strip, or two `sed -i` renames racing — so each function acquires the shared advisory lock `$HOME/.bashrc.lock` (fd 200, `flock -w 600 200`) *before* invoking its installer and holds it through the strip and the `.bashrc.bak.*` sweep, releasing only afterward (`flock -u 200`); codex and grok are the only two `~/.bashrc` writers in the parallel batch, so this fully serializes their install+strip against each other. `update_grok`'s installer leg is additionally wrapped in `timeout 300` (defense-in-depth beyond curl's own `--max-time`, since a hung `sh` after the pipe wouldn't otherwise be bounded) so a stuck install can't pin the lock indefinitely. (2) **the bun/npm global package store** — the inline `bun install -g kanna-code` batch-1 job, `update_gemini`'s and `update_opencode`'s `bun install -g` calls, and the `npm install -g` fallbacks in `update_codex`/`update_grok` all share one global store that doesn't tolerate concurrent writers, so each wraps its install in `flock -w 600 9 ... 9>"$HOME/.maude-pkg-install.lock"`. Lock ordering is deadlock-safe: fd 200 (`.bashrc.lock`) is always acquired before fd 9 (`.maude-pkg-install.lock`) inside codex/grok, and nothing that holds fd 9 ever reaches for fd 200, so there is no cycle. (Verified with a concurrent stress test exercising the lock against itself, which passed reliably with the lock held and failed without it.) No other job touches a file another job also touches — `update_skills` writes only its own `~/.claude/skills/{claude-api,doc-coauthoring,...}` subdirs, distinct from the per-tool skill/config paths.

The rest of the command runs sequentially, after the join, in this order: shell environment exports — idempotently appends `COLORTERM=truecolor`, `PYTHONDONTWRITEBYTECODE=1`, `GEMINI_CLI_TRUST_WORKSPACE=true` to `~/.bashrc` if missing; `python3 maude.py --fix-bashrc` — repairs orphan `fi` artefacts left by an older buggy keychain stripper (needs the freshly downloaded `maude.py`, and needs codex/grok's `~/.bashrc` edits finished — both guaranteed by the join); systemd user-session health check — unmasks `user@.service` if an old bootstrap masked it (prints `wsl -d Maude -u root` one-liner when root is required), installs `dbus-user-session` via mom if missing; `ensure_textual` — enforces the pin `textual>=8.2.4,<9`; prints the kanna/gemini/codex/opencode/grok results captured from the parallel batch above; `ensure_tool_symlinks`; `mom upgrade -y` — gated on `mom >= 0.2.20`, compares systemd version before/after and warns to run `wsl --shutdown` if it changed; prints the `update_skills` result captured from the parallel batch; writes the version stamp (`~/.local/share/maude/version`) from git or the GitHub API and prints it. When adding a new auto-updatable network-bound component, add it to the parallel batch (respecting the libs-first / no-bashrc-race constraints above); local/fast or package-manager steps stay sequential.

### `MAUDE_RAW` environment override

`maude-bootstrap.sh`, the `maude` CLI, and `lib/refresh-md.sh` all honor `MAUDE_RAW` to override the GitHub raw base URL (default `https://raw.githubusercontent.com/dirkpetersen/maude/main/light`). Setting it lets contributors test fork/branch changes without merging to `main` — e.g. `MAUDE_RAW=https://raw.githubusercontent.com/me/maude/feature/light maude tui`. `root-bootstrap.sh` hardcodes the URL and does NOT honor the override (it runs once at install time from `setup-wsl-maude.ps1`, which uses its own `-Release <tag>` flag with checksum verification for the same purpose).

### Two-phase bootstrap
`root-bootstrap.sh` writes `/etc/wsl.conf` (`automount=false`, default user, `interop=false`) and `/etc/fstab`. These only take effect after `wsl --terminate`. The setup script terminates WSL after root-bootstrap, then runs `maude-bootstrap.sh` as the maude user in the restarted distro.

### Host-persistent paths
`~/.claude` is a symlink to `~/Maude/.claude`. `~/.claude` and `~/.kanna/data` survive teardown/reinstall because they live on the drvfs mount. `~/.kanna` is a real local directory (kanna >= 0.78 needs a unix socket there, which drvfs cannot hold); only `~/.kanna/data` is a symlink to `~/Maude/.kanna/data`. `ensure_kanna_layout` (lib/kanna.sh) migrates old installs. Troubleshooting: "kanna is already starting" means kanna >= 0.78 with `~/.kanna` on drvfs; the layout migration fixes it. The `~/.kanna` root files (keybindings.json, llm-provider.json, cloud.json, pi sessions, machine-name) are local and do not survive reinstall. Any file that must survive reinstall must live under ~/Maude.

### Sandbox docs lifecycle

Three sandbox-facing docs live in `light/` with distinct lifecycles — easy to confuse:

- `light/MAUDE.md` — sandbox rules for the AI agent. Refreshed daily by `refresh_claude_md()` in `lib/refresh-md.sh`: downloaded to a tempfile, validated (non-empty, ≥200 bytes, first line matches `^# Maude Sandbox` — defends against corporate-proxy HTML interception), then moved to the cache at `~/.local/share/maude/MAUDE.md` and always `cp -f`'d over `~/.claude/MAUDE.md`. The `maude` CLI also re-runs this refresh on each project open, so edits to `~/.claude/MAUDE.md` are silently overwritten — change `light/MAUDE.md` instead.
- `light/CLAUDE.template.md` — 7-line user-instructions template. Copied to `~/.claude/CLAUDE.md` **only if that file does not already exist**. The template loads MAUDE.md via `@MAUDE.md` on line 2 — do not remove that line.
- `light/DANGER-ZONE.txt` — plain-English safety warning for the shared host folder. Auto-restored on each login by `welcome.sh` if missing from `~/Maude/DANGER-ZONE.txt`. References Microsoft Azure and Amazon Web Services as cloud AI providers and the SLAs/DPAs governing data handling.

### Login-time shell wiring (`welcome.sh` + `maude-shell.sh`)

`welcome.sh` is split into a thin, permanent root-owned stub and a user-owned copy carrying the real logic — so welcome/prompt edits reach existing sandboxes via `maude update` instead of being stuck at a one-time root-only install:

- **`/etc/profile.d/maude-welcome.sh`** (source: `light/welcome-stub.sh`) — a thin stub installed once by `root-bootstrap.sh`, never refreshed afterward (deliberately frozen, so it must stay minimal and correct). It sources `~/.local/lib/maude/welcome.sh`; if that user copy is missing, it self-heals with a best-effort, one-time `curl` of `light/welcome.sh` from GitHub — downloaded to a same-directory temp, **validated** (non-empty + `MAUDE_WELCOMED` marker) and atomically `mv`d into place before sourcing, so a partial or proxy-intercepted (HTML block-page) download is never sourced and never left persisted — gated on `[ -t 1 ]` so it only runs on an interactive terminal, and silent on failure so a broken network never blocks login. This validation matters because the stub is frozen: a corrupt user copy would otherwise be sourced on every login until the next `maude update`.
- **`~/.local/lib/maude/welcome.sh`** (source: `light/welcome.sh`) — the real welcome logic, user-owned. Seeded for the initial user by `root-bootstrap.sh` and refreshed on every `maude update` run (`update_all()` validates the fresh download is non-empty and contains `MAUDE_WELCOMED`, writing to a same-filesystem temp for an atomic replace). On a **legacy** sandbox whose `/etc/profile.d/maude-welcome.sh` is still the old full script (not the stub — detected by that file not referencing the `.local/lib/maude/welcome.sh` path), `update_all()` prints a yellow note plus the exact `wsl -d Maude -u root -- …` one-liner to install the stub, since refreshing the user copy has no effect on the login until then. It auto-restores `~/Maude/DANGER-ZONE.txt` if missing (`curl --max-time 10`); bootstraps keychain via `eval "$(keychain --quiet --noask --eval --agents ssh)"`, and if `~/.ssh/id_ed25519` or `~/.ssh/id_rsa` exists and its fingerprint is not already loaded, prints a colored "Unlock your GitHub SSH key" prompt and runs `keychain --quiet --eval --agents ssh <key>`. After keychain, if the TUI is enabled it runs `maude tui` and returns; the static ASCII welcome banner is the fallback for opt-out users (appends a yellow "Set Creds" nudge when neither `~/.aws/credentials` nor `~/.azure/clauderc` exists). All branches gate on `MAUDE_WELCOMED` so re-sourcing from `.bashrc` doesn't re-trigger.

Both the stub (`/etc/profile.d/maude-welcome.sh`) and `/etc/profile.d/maude-shell.sh` are installed by `root-bootstrap.sh`, which also appends explicit `. /etc/profile.d/maude-*.sh` lines to `/etc/skel/.bashrc` and the active user's `~/.bashrc` (profile.d only auto-runs for login shells, so the `.bashrc` hook is required for non-login interactive shells). That `.bashrc` hook still points at `/etc/profile.d/maude-welcome.sh` — now the stub, which transitively loads the user-owned `welcome.sh`.

- `maude-shell.sh`: exports `PIP_BREAK_SYSTEM_PACKAGES=1` (safe inside the sandbox — pip without a venv is intentional) and `COLORTERM=truecolor` (Windows Terminal renders 24-bit natively; this hint makes vim/tmux/fzf emit true-color escapes — `TERM` stays `xterm-256color`); sets `PS1` to `user@_:cwd$` (literal underscore in place of the hostname so the WSL distro name doesn't leak into the prompt); defines `menu()` as a shortcut for `maude tui`; overrides bare `help` to print "Please type 'maude help <ENTER>' for help" (delegates to `builtin help` when given args); and registers `complete -F _maude_complete maude` for tab completion of subcommands plus project names from `~/Maude/Projects/`.

### Double brackets in bash
Always use `[[ ]]` not `[ ]` in bash conditionals.

### `curl.exe` not `curl` in PowerShell
`curl` in PowerShell aliases to `Invoke-WebRequest`. Always use `curl.exe` explicitly. Also note `iex` may be blocked by antivirus on corporate machines. User-facing download commands use `curl.exe --ssl-no-revoke -fSLo <file> <url>`: corporate TLS inspection breaks Windows schannel revocation checks (CRYPT_E_NO_REVOCATION_CHECK), and `-f` surfaces HTTP failures instead of saving an error page.

### WSL encoding gotcha
`wsl.exe --list --verbose` outputs UTF-16LE with BOM. Strip null bytes before parsing:
```powershell
$raw   = wsl.exe --list --verbose | Out-String
$clean = $raw -replace "`0", ""
```

### Windows Terminal profiles
WT auto-generates profiles with `source=Microsoft.WSL` — they cannot be deleted, only hidden with pre-hidden stubs. WT profile cleanup must run **before** self-elevation (elevated process has a different `$env:LOCALAPPDATA`).

## Platforms (`maude.py`)

One `light/maude.py` serves all platforms: the Linux WSL sandbox (fetched daily from main), Windows (bundled in `maude.exe`, entry `maude_exe.py`) and macOS (prepared, untested; see `docs/windows-exe.md`). The platform section sits right after the imports:

- `PLATFORM` is `"windows"`, `"macos"` or `"linux-sandbox"` (anything else keeps Linux behaviour). Also `FROZEN`, `IS_WIN`, `IS_MAC`, `SANDBOXED`, `NATIVE` (= not sandboxed) and `HAS_SANDBOX` (Windows: WSL distro present; macOS: False = no-sandbox mode, red logo, no caption). Do not detect WSL via WSLInterop (interop is off in the sandbox).
- `FEATURES` is the feature map, one line per feature (`web`, `togithub`, `github`, `creds`, `update`, `autostart`) with a column per platform. `on_mount` hides the widgets of the features that are off (`hidden_widgets()`); a package that ports a feature flips its own line. Web UI and Autostart stay off on Windows and macOS; Set Creds, Update Maude, To Github and Setup Git(hub) are on (hidden set on both: `#btn-web`, `#autostart`). `update` is on everywhere: in the sandbox it runs `maude update`; on Windows/macOS `UpdateMaudeScreen` calls `native_update()` instead (Windows: `maude_exe.stage_exe()` = download + verify the latest release `maude.exe` + `.sha256` into a staged file only; `apply_staged()` swaps it in (rename-aside) in `run_tui` after the TUI exited with 42, never while it runs; then `claude update`, then `wsl.exe -d Maude -- bash -lc "maude update"` when `HAS_SANDBOX`; macOS: `fetch_maude_py()` + `claude update`). Reload exits 42 (Close/Escape reload too once an exe is staged; any other exit deletes the staged file); `maude_exe.run_tui` swaps and relaunches the exe on 42, `maude.py`'s `__main__` execs itself. `dev` builds are never replaced. Tested by `tests/test-update-native.sh`; see `docs/windows-exe.md`.
- `plat_*` helpers hold the per-platform code, Linux bodies unchanged: `plat_projects_dir()`, `plat_outside_projects()`/`plat_add_outside()`/`plat_remove_outside()` (Windows registry via `mx`, macOS JSON `~/.maude/projects.json`), `plat_tool(name)`, `plat_real_claude()`, macOS install offers (`mac_install_plan(tool, have_brew)` pure, `mac_ensure_tool` runner, `mac_offer`: claude and Kiro via their curl installers run with `pipefail` (claude puts its binary in `~/.local/bin`; the Kiro script on macOS installs `Kiro CLI.app` to `/Applications` and opens it, so Maude hints to open the app once if the command is not found), git via `xcode-select --install` (GUI dialog) or `brew install git`, gh/opencode/crush via brew or a printed hint; never sudo, never installs Homebrew, asks `[y/N]` with the command shown, re-resolves with `plat_tool`; on macOS `plat_tool("git")` is None for Apple's `/usr/bin/git` stub until `xcode-select -p` succeeds, see `mac_clt_ready`; wired into `open_project`/`_open_other_tool` and the Setup Git(hub) wizard; tested by `tests/test-mac-install.sh`), `plat_claude_env()` (`{}` in the sandbox; on Windows/macOS the clauderc + wrapper rules, see below; `_child_env()` merges it into every child process, a `None` value removes a variable), `plat_open_url()`.
- **Credentials path**: `clauderc_path()` is the only place that names the clauderc: sandbox `~/.azure/clauderc` (the `~/bin/claude` wrapper keeps reading it), Windows/macOS `~/.maude/clauderc` (via `maude_dir()`, same `export K='V'` format (single-quoted), same `parse_clauderc`/`merge_clauderc`, `.inactive` toggle the same). Never write `.azure` anywhere else. Bedrock (`~/.aws/credentials` + `config`) and Gemini (`~/.gemini/.env`) keep their paths on all platforms. `claude_env_from()` (pure) mirrors the wrapper precedence for Windows/macOS and applies it only when a clauderc exists (no clauderc = inherited env unchanged; Bedrock only if saved via Set Creds); non-Claude tools get the raw exports only (`_child_env(tools=True)`). clauderc lines are written `export K='V'` (bash-safe, `_sh_quote` also drops NUL and every line-break character `str.splitlines()` knows: CR LF VT FF FS GS RS NEL U+2028 U+2029; `parse_clauderc` splits on `\n` only, strips a trailing `\r`, and also reads the old `"V"` form; a hand-written `"$HOME/x"` value (expanded by bash when sourced) becomes a literal `'$HOME/x'` after any save from Set Creds, which rewrites every line; every reader sources the file: wrapper, `lib/llm-mode.sh`, the reviewer SKILL.md probes) and an undecodable file is refused, never overwritten. `write_aws_credentials` replaces only the `[bedrock]` / `[profile bedrock]` section (other profiles byte for byte, one-time `.maude-bak` copy, chmod 0600 where the OS has modes) on all platforms. `maude_exe.run_windows` picks the env up through `mx.child_env` / `_creds_env()`. Tested by `tests/test-creds-native.sh`.
- `from __future__ import annotations` must stay (macOS system Python is 3.9). Keep the shebang, `def maybe_self_update` and the column-0 `if __name__ == "__main__":` (the self-update validators grep for them). Tested by `tests/test-platform.sh`.
- `list_projects()` reads `origin` from `.git/config` in Python (`git_origin_from_config`, follows `gitdir:` files and worktree `commondir`); it asks `git config` only when the file uses `[include]` or cannot be parsed.

**Key behaviors:**
- **Open project**: `app.suspend()` → `claude <model> --continue` (fallback: `claude <model> --resume` only if the project has saved sessions, then `claude <model>`, each if the previous exits non-zero) → resume TUI; cursor restored to the project just opened. The sidebar **Clear History** checkbox (`#fresh-context`, first of the toggle column under the pickers) sets `fresh=True`, which makes `open_project()` skip `--continue` and start Claude with no prior history
- **Delete**: confirm modal → soft-delete to `Projects/.deleted/` (not permanent)
- **New project**: modal, spaces auto-replaced with hyphens, git init
- **Web UI**: before launch, `_kanna_fix_version` (lib/kanna.sh) reinstalls kanna when the installed version differs from the pin (the TUI suspends so the user sees the 2-minute wait). Launches kanna with `CLAUDE_EXECUTABLE=$HOME/bin/claude` so the wrapper sets auth env vars (Foundry/Azure/Bedrock/direct). Click again to stop — `SIGTERM` → `SIGKILL` + `fuser -k 3210/tcp`. Refuses to launch without credentials; pops `CredsEntryScreen` as recovery
- **To Github**: dual-mode push/detach for the selected project. If `origin` already points to GitHub, opens `DetachFromGithubScreen` which removes the local `origin` remote only — it explicitly does NOT delete the GitHub-side repo (leaves it orphaned; must be deleted manually on github.com). Otherwise opens `PushToGithubScreen`, which: (1) auto-seeds a minimal `README.md` (`# {repo}\n`) if none exists in any case variant, (2) forces `GIT_SSH_COMMAND='ssh -o BatchMode=yes -o StrictHostKeyChecking=accept-new'` so a misconfigured SSH state errors in 5-10s instead of blocking on a passphrase prompt, (3) short-circuits with a clear error and auto-pops `SSHKeyUnlockScreen` if the SSH key has a passphrase but no agent has it loaded, (4) runs `gh repo create --push` for new repos or `git push -u origin HEAD` for existing ones, creating an initial commit first if the project has no HEAD
- **Native Git/SSH (Windows/macOS)**: To Github, SSH unlock and Setup Git(hub) run natively with `git_exe()`/`gh_exe()` (`plat_tool`). One SSH stack per platform via `ssh_tool()`: Windows = `System32\OpenSSH` (ssh, ssh-keygen, ssh-add; its ssh-agent service is only detected, never started, no admin), macOS = `/usr/bin` (Apple agent, `ssh-add --apple-use-keychain`, `UseKeychain`/`AddKeysToAgent` appended to `~/.ssh/config` only if absent). MinGit's ssh tools are not used (no ssh-keygen, MSYS agent). `GIT_SSH_COMMAND` = `git_ssh_command()` (that ssh + BatchMode). Passphrases go to ssh-add/ssh via `SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force` and a static helper reading `MAUDE_ASKPASS_PW` from the environment (`.cmd` with delayed expansion on Windows), never to disk. Signing is SSH signing, no gpg: `gpg.format ssh`, `user.signingkey <id_ed25519.pub>`, `commit.gpgsign true`, `gpg.ssh.program` = the platform ssh-keygen, it is only switched on after `signing_roundtrip()` (a real non-interactive `ssh-keygen -Y sign`) succeeds and never overwrites an existing signing setup (`signing_conflict()`); `core.sshCommand` is a separate step (`apply_ssh_command()`: Windows + MinGit only, skipped if set or `GIT_SSH`/`GIT_SSH_COMMAND` exist). Windows never falls back to a bare-name `ssh-keygen` (`openssh_available()`), and never silently `ssh-add`s an unencrypted key (the Windows agent persists keys). The key is uploaded with `gh ssh-key add - --type signing` and `gh auth login --web --skip-ssh-key --scopes admin:ssh_signing_key`. No `mom`/keychain package/`.bashrc` block there; the sandbox paths below stay as they are. Helpers are pure and tested by `tests/test-git-native.sh`; see `docs/windows-exe.md`.
- **SSH key unlock at TUI mount**: on mount (and again after Setup Git(hub) finishes), if `~/.ssh/id_ed25519` exists, an ssh-agent is reachable (`ensure_ssh_agent()` will spin one up), and the key isn't already loaded, the TUI auto-pops `SSHKeyUnlockScreen` for the passphrase — or silently runs `ssh-add` with an empty passphrase if the key is unencrypted. Windows/macOS (native): if an agent is already reachable (Windows ssh-agent service, macOS launchd agent) there is no prompt at mount (macOS still runs `ssh-add --apple-load-keychain`); the passphrase is then asked only on demand by To Github. The prompt appears natively only when Maude had to start its own agent (macOS). This is the deliberate counterpart to the Setup Git wizard's keychain block (which omits a key file on purpose). If you ever "fix" the wizard by passing the key to `keychain`, you'll re-introduce an early `.bashrc` prompt before the TUI is visible — leave the unlock to the TUI
- **Setup Git(hub)**: `GitSetupWizard` 4-step modal — (1) GitHub username → `api.github.com/users/<name>` lookup pre-fills name/email (email falls back to `<id>+<login>@users.noreply.github.com` when hidden); (2) ed25519 SSH key detect/generate + verify via `ssh -T git@github.com` (manual paste of the pubkey to github.com); (3) `gh auth login --hostname github.com --git-protocol ssh --web --scopes write:gpg_key`, then silently generates an ed25519+cv25519 GPG signing key (no passphrase) and uploads it via `gh gpg-key add` — no separate GPG step is shown to the user; (4) `git config user.name`/`user.email`/`init.defaultBranch=main` (plus `user.signingkey` + `commit.gpgsign=true` when GPG was provisioned), `mom install -y keychain`, and a sentinel-bracketed (`# >>> Maude keychain BEGIN`/`END`) keychain block appended to `~/.bashrc`. The keychain block intentionally does NOT pass a key file — `SSHKeyUnlockScreen` handles the passphrase prompt at TUI startup instead, so `.bashrc` doesn't block on a prompt before the TUI appears
- **"Perplexity MCP" checkbox**: under Clear History, off by default. State is the flag file `~/.maude-perplexity` (exists = checked). `sync_perplexity()` runs at the start of `open_project()`: checked and connector missing -> `claude mcp add --transport http --scope user perplexity-computer https://www.perplexity.ai/rest/computer/mcp` then `claude mcp login`; exists but not Connected -> login only; unchecked does nothing at project open; unticking the box runs `claude mcp remove --scope user` once (`remove_perplexity()`), so a connector added by hand is never touched while the box was never ticked. The connector is user-scope MCP config in `~/.claude.json`. Failures only print a warning; the project always opens. Tested by `tests/test-perplexity-sync.sh`
- **Claude model picker**: 4-button radio (`opus` default, `fable`, `sonnet`, `haiku`). Persists to `~/.maude/maude-model` as `<model>[,<thinking-level>]` (e.g. `opus,high`; `opus` alone = default level); the same file on Linux, macOS and Windows (`%USERPROFILE%\.maude\maude-model`; no registry). The legacy `~/.maude-model` is moved into it once (value copied, old file deleted). `maude_dir()` (maude.py) / `maude_exe.maude_dir()` create `~/.maude` with mode 0700 (no effect on Windows) and are meant to be reused for other per-user state. Bad model -> `opus`, bad level -> default. Passed to `claude <model> [--effort <level>] --continue` when opening projects. On Windows the tip reads `Paste image  Alt+V` instead of `Share image`.
- **Thinking picker**: third radio column right of the AI tool picker: `auto` (default, passes nothing), `low`, `medium`, `high`, `xhigh`, `max`. Mechanism: Claude Code's `--effort <level>` flag (`claude --help`: low, medium, high, xhigh, max). Claude Code only (other tools ignore it); saved as the second field of `maude-model`; also applied by `maude.exe` (`run_windows`, `OPEN_SH` inside WSL). Pure helpers `parse_model_pref()`/`format_model_pref()`/`effort_args()` are tested by `tests/test-ai-tools.sh`.
- **Toggles**: one column of one-line checkboxes under the pickers, box left of the label: `Clear History` (`#fresh-context`, fresh=True skips `--continue`), `Perplexity MCP` (`#perplexity`), `Autostart` (`#autostart`, hidden on Windows).
- **AI tool picker**: 4-button radio to the right of the model picker (`Claude Code` default, `Kiro CLI`, `OpenCode`, `Crush`), persisted to `~/.maude/maude-tool` (same on every platform, `%USERPROFILE%\.maude\maude-tool` on Windows; the legacy `~/.maude-tool` is moved into it once). Non-Claude tools run in the project dir: `kiro-cli chat [--resume]` (device-code sign-in via `kiro-cli login --use-device-flow` if `kiro-cli whoami` fails), `opencode [--continue]`, `crush [--continue]`; the Claude model is NOT passed to them (they start on their own default model), Perplexity sync runs only for Claude Code, and a missing binary prints a hint to run `maude update`. Fable only exists in Claude Code: picking `fable` selects Claude Code, picking another tool while `fable` is set switches the model to `opus` (also reconciled at startup). Pure helpers `tool_command()`/`reconcile()` are tested by `tests/test-ai-tools.sh`. Kiro CLI and Crush are installed by `maude-bootstrap.sh` and, if missing, by `maude update` (`lib/cli-tools.sh`); `~/.kiro/skills` is symlinked to `~/.claude/skills`.
- **Credential gate**: `CredsEntryScreen` blocks startup when no LLM credentials are found — checks a native claude.ai login (`have_claude_login()`: non-empty `claudeAiOauth.accessToken` in `~/.claude/.credentials.json` with `expiresAt` in the future, mirroring `_is_claude_logged_in()` in the dok claude-wrapper), `ANTHROPIC_API_KEY`, `ANTHROPIC_FOUNDRY_API_KEY`, non-empty `~/.aws/credentials`, or non-empty `~/.azure/clauderc` (`~/.maude/clauderc` on Windows/macOS). Three mode tabs plus one action button. **Claude Login** (next to Azure Foundry) suspends the TUI and runs the **unwrapped** `~/.local/bin/claude /login` — unwrapped because with zero cloud creds the `~/bin/claude` wrapper exits "No valid configuration found" before Claude Code starts, so `/login` could never complete through it; interop is off, so the user copy/pastes the OAuth URL into a Windows browser manually. **On Windows/macOS** the same button runs the real claude (`plat_real_claude()`) with `/login` and the browser opens natively (no copy/paste text); a login counts when `~/.claude/.credentials.json` shows one or `claude auth status` says `loggedIn`. **Native gate** (`creds_gate_decision()`): there the gate never locks anyone out. It shows only when claude itself answers "not logged in" and nothing is configured (login file, env vars, `~/.aws/credentials`, `~/.maude/clauderc`); an unknown status (claude missing, timeout) does not block, and Cancel still opens the project. `claude auth status` runs in a worker thread (notice "Checking sign-in...") and a True answer is cached for the session; `have_claude_login()` also accepts an expired access token while a refresh token is valid (the wrapper rule, which also applies in the sandbox). Credentials are written to `clauderc_path()` (`~/.maude/clauderc` natively) and loaded by Maude itself into every AI tool it starts. On return, a valid token dismisses the modal as saved (pending action proceeds); otherwise a status hint shows. The wrapper prefers a native login over Foundry/Bedrock, and `--az`/`--aws` force a specific cloud per-run. The three mode tabs: **Paste exports** (parses `export KEY=VAL` / `KEY=VAL` lines whose key starts with `ANTHROPIC_*/CLAUDE_*/AWS_*/AZURE_*/OPENAI_*/GEMINI_*/GOOGLE_*`, merges into `~/.azure/clauderc` mode 0600 — **except** `GEMINI_*`/`GOOGLE_*`, which are split out to `~/.gemini/.env` (dotenv format, mode 0600) where the Gemini CLI auto-loads them; those exist solely to feed the gemini-cli skill, do NOT touch clauderc, and do NOT satisfy the Claude-credential startup gate; there is intentionally no Gemini tab/button. Empty-valued lines (`FOO=`) are dropped. `finalize_gemini_vals()` then picks a Gemini-CLI auth mode that actually authenticates: a bare API key (`GEMINI_API_KEY`, or `GOOGLE_API_KEY` mapped onto it) is routed to **AI Studio**, which accepts API keys with no OAuth; **Vertex** (`GOOGLE_GENAI_USE_VERTEXAI=true`) is enabled only on real intent — the flag is in *that* paste, or a service account / ADC (`GOOGLE_APPLICATION_CREDENTIALS`) is configured — because Vertex *rejects* plain API keys for `generateContent`. When an API key is used, any stale `GOOGLE_GENAI_USE_VERTEXAI=true` is flipped back to `false` so the user isn't trapped on the Vertex path; Vertex-with-no-region defaults to `us-west1`/Oregon (`DEFAULT_VERTEX_LOCATION`). The gemini CLI's untrusted-directory gate is bypassed via `GEMINI_CLI_TRUST_WORKSPACE=true` (set in `maude-shell.sh`) plus `--skip-trust` in the skill); **AWS Bedrock** (writes `~/.aws/credentials` + `~/.aws/config` under a `[bedrock]` named profile, also stashes `AWS_*` + `CLAUDE_CODE_USE_BEDROCK=1` in clauderc); **Azure Foundry** (URL + API key → clauderc with `CLAUDE_CODE_USE_FOUNDRY=1`). When *both* Bedrock and Foundry creds exist, a "Default to AWS Bedrock" checkbox appears that physically renames `~/.azure/clauderc` ↔ `~/.azure/clauderc.inactive` so the claude wrapper doesn't re-source Foundry creds when Bedrock should win
- **Auto-launch**: the welcome stub at `/etc/profile.d/maude-welcome.sh` (installed once by `root-bootstrap.sh` and *also* explicitly sourced from `~/.bashrc` to cover non-login interactive shells) loads the user-owned `~/.local/lib/maude/welcome.sh`, which runs `maude tui` when all four guards hold: `[[ -t 1 ]]` (stdout is a TTY), `MAUDE_WELCOMED` is unset (set on first run to prevent re-launch when `.bashrc` re-sources the script), `~/.maude-tui-disabled` does NOT exist, and `maude` is on PATH. The sidebar checkbox is an OPT-OUT bound to `not DISABLE_FLAG.exists()`: unchecking touches `~/.maude-tui-disabled`, rechecking unlinks it. The legacy `~/.maude-tui-autostart` flag is no longer consulted — remove references when seen
- **Daily self-update**: `maybe_self_update()` runs at module entry, before `app.run()`. Compares `~/.maude-tui-last-update` (format: `YYYY-MM-DD`) against today; if stale and time ≥ noon local, downloads fresh copy from GitHub and atomically replaces itself. New code takes effect on next launch
- **Status line**: `~/.claude/statusline.sh` renders cwd + remaining context-window %. Bootstrap merges this into `~/.claude/settings.json` `statusLine.command` without overwriting existing user customisations
- **Exit hint**: after quitting TUI prints "Please type menu \<Enter\> to get back to the TUI or type maude help \<Enter\>"
- **Colors**: green logo, dusty-rose accents, warm-grey toggles (overrides Textual default blue on `Checkbox`/`RadioButton`)
- **Dependency**: `textual` — installed via `pip install textual` in `maude-bootstrap.sh`; pin `textual>=8.2.4,<9` — 8.2.3 crashes `CredsEntryScreen` on open with `KeyError: text-area--gutter` (textual#6528); later 8.x could still raise it (or `NoMatches`) when the mode buttons were pressed rapidly, because `remove_children()`/`mount()` overlapped, until `CredsEntryScreen` kept its three mode panes always mounted from `compose()` (`_switch_mode` only toggles `display` and the button variants, nothing is removed or re-mounted; `save()` reads only the pane of the active mode); `<9` shields auto-updating machines from an unknown future major break
- **`maude.py` CLI flags** (exit before `maybe_self_update()` and the TUI): `--github` runs `GitSetupWizard` standalone in a minimal `_WizardApp` (invoked by `maude github`); `--fix-bashrc` runs `fix_bashrc_orphan_fi()` to repair `~/.bashrc` damage left by an older buggy keychain stripper (invoked by `maude update`). The orphan-fi repair function looks unused but is load-bearing — do not remove during dead-code cleanups

## PATH convention

`~/bin` must be at the **front** of PATH; `~/.local/bin` must also be present. `maude-path.sh` (written to `/etc/profile.d/` by `root-bootstrap.sh`) runs at the **end** of `~/.bashrc` — after tool installers like Claude Code that prepend their own paths — then re-enforces `~/bin` first and deduplicates `~/.local/bin`.

## Credential forwarding (kanna web UI)

Kanna is launched with `CLAUDE_EXECUTABLE=$HOME/bin/claude` so it shells out to the Maude wrapper, which sets the appropriate auth env vars per invocation. If the wrapper is missing, the env var is unset and kanna falls back to plain `claude` on PATH.
